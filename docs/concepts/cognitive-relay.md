# CognitiveRelay

## What it is

`CognitiveRelay` is a provider-agnostic LLM router that sits between
`AgentLLMService` and the actual model call. It evaluates declarative
`RoutingRule`s in order against a `RoutingContext` (cognitive phase,
agent identity, task hints) and resolves an `AIConfiguration` to use.
The first matching rule wins; if no rule matches, the agent's default
configuration is used as fallback. Every routing decision emits a
`RoutingEvent`.

A resolved configuration carries two facts that used to be one. Its
**maker** travels with its model (`AIModel.makerId`: Anthropic makes
Claude); its **route** is its provider — whose endpoint and key carry the
call. Usually they coincide. `AIProvider_OpenRouter` is a route that is
not a maker: `OpenRouterConfig(model = Claude.Sonnet5)` holds the same
model object `AnthropicConfig` does, and only `AIConfiguration.wireModelId`
differs — the slug from `OpenRouterModelSlugs` rather than the model's
name. The relay chooses a model; the route decides only how it is reached
(AMPR-434). `AIProvider.ALL_PROVIDERS` lists the makers, and the catalogue
built from it has one row per model whatever the route. A call's record
keeps the two apart the same way: `providerId` is the maker, and `via` is
the route when it is not the maker's own endpoint (AMPR-436).

## Why it exists

The cognitive layer must not import provider SDKs directly. Three
consequences fall out of that single rule:

1. **Multi-provider portability.** The same agent code runs against
   Anthropic, OpenAI, Google, and any future provider, because the choice
   of provider is *data* (`AIConfiguration`), not *imports*.
2. **Phase-aware model selection.** The PROPEL loop has phases with very
   different latency / quality / cost profiles. Routing rules can use
   `CognitivePhase` in the context to send `PERCEIVE` to a cheap fast
   model and `PLAN` to a more capable one — without the agent code
   knowing or caring.
3. **Observable, replayable decisions.** Every routing decision is an
   event. `ArcTraceProjection` reads `routingReason` from the matched
   `ProviderCallStartedEvent` to show in the trace *why a particular
   model was chosen for a particular phase*. Bypassing the relay means
   bypassing this story, and the trace shows a model call with no
   explanation.

The relay also decouples agent code from configuration churn: switching
the `PERCEIVE` phase to a different model is a config change, not a code
change.

## Where it lives

- `agents/domain/routing/CognitiveRelay.kt` — the interface; `resolve` and `resolveWithMetadata`.
- `agents/domain/routing/CognitiveRelayImpl.kt` — production implementation that matches rules.
- `agents/domain/routing/CognitiveRelayPassthrough.kt` — test/dev helper that always returns the fallback.
- `agents/domain/routing/RelayConfig.kt` — the rule set.
- `agents/domain/routing/RoutingRule.kt` — predicate + target configuration.
- `agents/domain/routing/RoutingContext.kt` — what rules match against (`CognitivePhase`, `agentId`, hints, optional `requirements`).
- `agents/domain/routing/RoutingDecision.kt` — the event payload.
- `agents/domain/routing/ExecutionTags.kt` — the tag vocabulary an `ExecutionAssignment` (model, effort) contributes to a context, so a per-seat assignment routes through `RoutingRule.ByTag` rather than through a rule kind of its own (AMPR-413). Written by `roster/SeatRouting.kt` — see [TeamLayer](team-layer.md).
- `agents/domain/routing/capability/` — capability vocabulary (`ProviderCapability`, `CapabilityRequirement`, `CapabilityRung`) and the SDK-free `ModelDescriptor` + `ModelDescriptorRegistry` the `ByCapability` rule matches against, keyed per *model* rather than per provider (AMPR-214). Parallel to `domain/ai/model/AIModel` (left untouched).
- `agents/domain/routing/capability/ModelDescriptorSource.kt` — where a registry's catalog comes from. The framework ships the interface and `DefaultModelDescriptorSource` (the bundled cloud catalog); a consumer supplies its own.
- `agents/domain/routing/local/` — the on-device side. `LocalInferenceEngine` + `LocalCapacity` are the engine contract a platform binds, and `LocalGenerationRequest` is what one generation asks of it (AMPR-462); `InferenceLocality` + `InferenceLocalityClassifier` say where a call ran; `OnDeviceInferenceProjection` folds the relay's and the service's existing events into an `OnDeviceInferenceState`, which `OnDeviceInferenceMonitor` holds live for a surface (AMPR-327). `LocalUnavailableReason` is the one declaration of the reason codes an engine reports.
- `agents/domain/reasoning/AgentLLMService.kt` — the only legitimate caller. `call` returns the text; `callDetailed` returns the text plus the maker, model, route (`via`) and routing reason that produced it. The request carries the configuration's wire id (`AIConfiguration.toClientModelId()`), not the model's name.
- `llm/UpstreamLlmClient.kt` — the transport seam. `call` is prompt-in / completion-out; `callDetailed` returns an `UpstreamCompletion` that may carry a `ServedBy` naming what answered (AMPR-391). `callDetailed` has a default body wrapping `call`, so a transport implements one method or two.
- `llm/DispatchingUpstreamLlmClient.kt` — executes the relay's choice on the bound engine or the cloud transport, refuses a local-designated choice with `LocalEngineNotBoundException` when no engine is bound, and is the `InferenceLocalityClassifier` that knows which. Forwards `callDetailed` to whichever side it dispatched to.
- `llm/OpenRouterUpstreamLlmClient.kt`, `llm/OpenRouterRoutingPolicy.kt` — the gateway transport (AMPR-437). One Ktor POST that adds OpenRouter's `provider` object (by default: the maker's own hosting only, no fallback, `data_collection: deny`) and opts into `openrouter_metadata`, then returns a `ServedBy` with the maker, `via = openrouter`, `usage.cost` and `openrouter:<host>`. Pinned, it throws `UpstreamHostMismatchException` when the response names another host or none. Wired in nowhere.
- `llm/OnDeviceInferenceBinding.kt` — one engine bound to the relay that routes to it, the registry the relay and the client share, the dispatching client, and the monitor (AMPR-374). Every probe the client makes is attributed, adopts the engine's reported window, and lands in `state`. Both of the paths below are built on it.
- `llm/OnDeviceInferenceSession.kt` — the smallest complete local-first path: `ask` through `AgentLLMService`, `state` from the binding. Built on `OnDeviceAssistantAgent`, the display-text identity and the one bundled definition whose floor is rung `ZERO` (AMPR-372).
- `domain/arc/bridge/ArcSession.kt` — the Arc path. `create(…, engine, cloud)` hands the binding's relay and client to `AmpereRuntime` and exposes the binding's state as `onDeviceState` (AMPR-374). No Arc step is eligible for the device (AMPR-459), so an engine bound here is probed and shown but serves none of a run's calls. What it serves is `ArcSession.ask`, the Arc host's display-text path (AMPR-461): an `OnDeviceInferenceSession` built over the session's own binding (`OnDeviceInferenceSession.over`, internal), so one engine keeps one binding, one ledger and one indicator.
- `agents/domain/event/RoutingEvent.kt`, `TelemetryEvent.kt` (`ProviderCallStartedEvent`, `ProviderCallCompletedEvent`) — observability events.
- `llm/decide/` — the *other* outbound seam (AMPR-384). `UpstreamDecisionClient` is the sibling of `UpstreamLlmClient` for the Decide call kind: a state plus typed questions in, judgments out, no text. It does not route through the relay — a hosted decision endpoint's model is fixed by the endpoint, and the one adapter that is a generative model (`ModelBackedDecisionClient`) reaches the relay through `AgentLLMService` like any other call. See [DecideSeam](decide-seam.md).

## Invariants

- **Cognition code never imports a provider SDK.** Anthropic, OpenAI, Google clients live below `domain/ai/` and are addressed exclusively via `AIConfiguration`. A `import com.anthropic` (or equivalent) anywhere under `agents/domain/reasoning/` or `agents/domain/cognition/` is a violation.
- **All LLM calls go through the relay.** `AgentLLMService` is the single entry point. Direct construction of an `AIConfiguration` and a model client in domain code bypasses routing, observability, and rule precedence.
- **Routing rules are evaluated in declared order; first match wins.** Reordering rules changes routing behaviour. The relay is intentionally not "best match" — it is "first match", because predictability beats cleverness. The one principled exception is cost: when the first match is a `ByCapability`, selection is cheapest-capable across the capable candidates (still deterministic — a total order on cost-per-Watt with a `ModelDescriptor.modelName` tie-break, not a scoring engine).
- **Every resolved call emits `ProviderCallStartedEvent` and `ProviderCallCompletedEvent`.** With `cognitivePhase`, `providerId`, `modelId`, and `routingReason` populated. `ArcTraceProjection` joins these to build `ModelInvocationTrace`; missing events produce gaps in the trace.
- **The start names what was *requested*; the completion names what *served*.** The start row is published before the transport runs, so the resolved `AIConfiguration` is all it can name. When a transport reports a `ServedBy`, the completion, the `LlmCallResult` and the cost record name the served provider, model, usage and cost instead, and the completion's `providerId`/`modelId` may therefore differ from its start's (AMPR-391). That is why the pair is joined by the envelope's `caused_by` and not by provider+model equality. A transport that reports nothing is identical to before in every field.
- **A call's record names the maker in `providerId` and the route in `via`; `providerId` is never a gateway.** For a call resolved to configuration `c`, `AgentLLMService` records `providerId = c.model.makerId`, `modelId = c.model.name` and `via = c.provider.id` only when that differs from the maker (AMPR-436) — on both `ProviderCall*` events, on `LlmCallResult`, and through `ArcTraceProjection` on `ModelInvocationTrace`. A direct call's `via` is null and never encoded, so its record is byte-for-byte what it was before. The price follows: the bundled catalog is keyed `(providerId, modelId)` and holds makers only, so a routed call is priced at its maker's list price unless the transport reported a cost, and the catalog gains no gateway rows. `ServedBy.via` wins field by field like every other `ServedBy` field; null means direct or not stated and leaves the configuration's route standing. Only the wire id differs by route — `DispatchingUpstreamLlmClient` still dispatches on the model's own name.
- **A served fact outranks a derived one, and silence is not a fact.** Each `ServedBy` field is independently optional and each null means "I am not reporting this", never "there is nothing here": a null `usage` keeps the completion's own counts, a null `estimatedCostUsd` falls through to the bundled pricing catalog, a null `routingReason` leaves the relay's reason standing, a null `latencyMs` leaves Ampere's wall clock. A transport that blanked these by reporting zeros would silently erase accounting Ampere could otherwise derive.
- **Hot-swap goes through `updateConfig`.** Mutating a `RelayConfig` field in place is not supported. `updateConfig` exists so changes can be observed by long-running reasoning sessions. `updateConfig` swaps *rules*; `ModelDescriptorRegistry.refresh` swaps the *catalog*. They are separate seams and neither substitutes for the other.
- **A failed catalog load never empties the registry.** `refresh` replaces the catalog atomically or not at all: a `Result.failure` from the source leaves the previous catalog fully intact and surfaces the error. A registry that silently emptied itself would turn a transient network blip into blanket `FloorUnmet` — the exact silent downgrade the rung floor exists to prevent. A source that cannot produce a catalog must return `failure`, not an empty list.
- **Where a call ran is decided by what executed it, not by what was selected.** `ModelDescriptor.executesLocally` is the single predicate behind both dispatch and display, and `DispatchingUpstreamLlmClient.localityOf` adds the one fact the catalog cannot know: whether an engine is bound. "On-device" is a claim a person relies on, so anything not provably on the device is `CLOUD` — including a local-designated model with no engine to run on, which the dispatching client refuses rather than runs.
- **A local-designated configuration never leaves on a cloud transport.** When the resolved model `executesLocally` and no engine is bound, `DispatchingUpstreamLlmClient.call` throws `LocalEngineNotBoundException` before anything is sent, and `AgentLLMService` books it on `ProviderCallCompletedEvent.errorType` like any transport error (AMPR-371). `AIProvider_OnDevice.client` throws on read for the same reason: the stand-in provider has no host, and a default client would have POSTed the prompt to `api.openai.com` with an empty token. A model with no descriptor still goes to the bundled transport. Picking a cloud model *instead* is the availability gate's decision, made before the call.
- **An on-device failure is returned, never re-sent.** Availability is decided *before* the call, by the probe the relay's gate reads. Once a prompt has been routed to the device, a failed generation surfaces as a failure; it is not retried on a cloud model. A person shown "on-device" must not find out afterwards that their prompt left. A reply the model cut short at the call's output cap is not a failure at all: it is returned as it came, and nothing re-asks it in the cloud (AMPR-462).
- **The on-device read model is commutative.** `EventSerialBus` launches each handler on its own coroutine, so a `ProviderCallCompletedEvent` can be folded before its `ProviderCallStartedEvent`. `OnDeviceInferenceProjection` counts rather than tracks open calls, and keeps the later-timestamped fact rather than the last-folded one, so any order ends in the same state.
- **The context-window fit widens a requirement; it never creates one.** With an engine bound, `AgentLLMService` adds `minContextTokens` (system message + prompt + output budget) to a call's *existing* `CapabilityRequirement`, so the relay keeps a prompt that will not fit away from the small-window on-device model. A call with no requirement is left alone: a `ByCapability` rule cannot match without one, and sizing it would make a step eligible for the device that nothing declared eligible. Which calls may declare a floor the device clears is the rule below (AMPR-372), not the service's. Without an engine bound nothing is added, so cloud-only routing is unchanged.
- **A request is shaped by the model it resolved to, never by the rule that picked it.** `AgentLLMService` builds the request after resolution, from the resolved `AIModel`'s features and, for the name of the output cap only, its route. `temperature` is omitted where `supportsSamplingParameters` is false: the models that 400 on it, and every Gemini 3 and later model, which Google says loops or degrades below its default of 1.0 (AMPR-488). `reasoning_effort` is sent only to a model whose `defaultThinking` is set (Gemini 3 and later; OpenAI's GPT-5.5, GPT-5.6 and GPT-6, AMPR-501), and `ReasoningEffortPolicy` chooses it: the lower of what the call asks for (`preferredReasoning`, `requirements.minReasoning`, else the model's default) and what its `max_tokens` affords (`low` up to 2,000, `medium` up to 8,000), because the output cap includes thought tokens and a PROPEL call's cap of 500 or 1,000 is spent by default thinking. `minimal` and `none` are never sent, and the rung is not read: a floor says which model may serve, not how hard the call is. The cap goes out as `max_completion_tokens` on the direct `openai` route, where OpenAI's reasoning models 400 on `max_tokens`, and as `max_tokens` everywhere else (AMPR-501).
- **Rung ZERO serves display text only.** Display text is words a person reads, which nothing in the run acts on, decides on or remembers. Every PROPEL phase call — PERCEIVE, PLAN, EXECUTE tool arguments and tool-less reasoning steps, LEARN — and every judgment stays at rung `ONE` or above, and a per-call requirement never lowers an agent's floor (AMPR-229). The rule follows what consumes the output, which the framework can know, not what the prompt asks, which it cannot check: measured on the production engine path with the real builders' prompts, the on-device model restated single-source text 33 of 33 times and selected, compared, counted or attributed across items 5 of 33; LEARN would have stored a false learning in 15 of 18 replies, mostly at `high` confidence, and the goal-met judgment called 59.0% of unmet runs met against 15.0% for a rung-`THREE` cloud model on the same prompts, while 473 of 474 JSON replies parsed. Format compliance is not quality. Eligibility is per kind of call, not per agent or Arc step: display text runs under `OnDeviceAssistantAgent` through `OnDeviceInferenceSession`, and an agent that runs the loop declares `ONE` or above. This is a rule as of 2026-10-17, ratified on AMPR-372; the record is [`docs/ampr-372-rung-zero-eligibility.md`](../ampr-372-rung-zero-eligibility.md), and the code holds it at the five points below.
- **Five points keep loop work and judgments off the device (AMPR-459), and each is a raise or a refusal.** One per way such work used to reach it:
  1. *A floor on an Arc.* `ArcConfig` and `ArcAgentConfig` refuse a `minimumRung` below `ONE` at construction (`requireArcFloor`), so a manifest decoded from YAML or JSON fails where it is written.
  2. *A floor or a configuration on an agent.* `SparkBasedAgent` refuses a declared floor below `ONE`, and a configuration that names the on-device provider or an on-device model — the model too, because the dispatching client keys on it — read through `getAvailableModels()` so a configuration with backups is not resolved by the check. That covers `SparkAgentFactory`, `AgentFactory`, the role factories, every Arc step and every hosted seat.
  3. *A per-call requirement.* `AgentReasoning.callLLM` and `callLLMForJson` raise a forwarded requirement's floor to at least `ONE` with `maxOf`, so a stricter floor stands; a call with no requirement still forwards none. Every `SparkBasedAgent.callLLM` overload reaches it.
  4. *A re-rated on-device model.* `InMemoryModelDescriptorRegistry` refuses a catalog that rates a descriptor that `executesLocally` above `ZERO` — at seed and on `register` by throwing, on `refresh` as a failure that keeps the previous catalog — whether it came from a consumer's source, a YAML override or `register`. An unrated local model is legal: it fails every declared floor already.
  5. *The Decide adapter.* `ModelBackedDecisionClient` raises the floor of a requirement on its constructor's context to `ONE`, and forwards a context with none unchanged.

  A missing floor stays legal everywhere and keeps today's routing: with no requirement no `ByCapability` rule can match, so the call uses the agent's configured model, which point 2 keeps off the device. Nothing defaults to an explicit `ONE`, because that would switch every agent to cheapest-capable routing. The relay is untouched: a `ZERO` requirement still routes to the device, which `OnDeviceInferenceSession` depends on and `Rung0RoutingTest` and the `ampere-eval` Rung 0 bench pin. Two ways remain that this does not reach: an `AgentReasoning` or `AgentLLMService` built by hand on a `ZERO`-floored definition (including one passed to `SparkBasedAgent` as its reasoning override), and a consumer's own `ModelDescriptorRegistry` implementation, which holds whatever rule it implements.
- **An `ExecutionAssignment` routes as a tag, and a tag nothing names routes nowhere.** `ExecutionTags.of` turns the model and effort on an assignment into `model:<id>` / `effort:<level>` tags — one per property set, none for a property left null (`ExecutionTags.kt:43-46`) — which a consumer's `RoutingRule.ByTag` acts on. The framework cannot do more: `ExecutionAssignment.model` is opaque to Ampere (a provider's id or a consumer's alias for one), so nothing here can turn it into an `AIConfiguration`, and only the consumer's rule set holds that mapping. An assignment no rule names therefore changes nothing about where the call goes — it is a declaration on the context, not an override of the route.
- **A transport is opted into on each seam separately.** `AgentConfiguration.upstreamLlmClient` and `AgentConfiguration.upstreamDecisionClient` are independent; injecting one does not supply the other, and each has its own missing-client exception. The relay's "every call must produce some `AIConfiguration`" rule is about *selection*; it never conjures a transport.
- **The fallback is not optional.** A relay that can return null on no-match would make every `AgentLLMService` caller responsible for a fallback decision, defeating the point. Every call must produce some `AIConfiguration`.

## Common operations

- **Add a routing rule** — extend `RelayConfig.rules` with a new `RoutingRule` whose predicate examines `RoutingContext`. Order matters; more specific rules earlier.
- **Route by phase** — `RoutingContext.phase` is a `CognitivePhase`; rules can switch on it directly.
- **Route by capability** — set `RoutingContext.requirements` (a `CapabilityRequirement`) on the step and add `RoutingRule.ByCapability` rules ordered most-preferred-first. Each matches only when its target provider's `ProviderDescriptor` (looked up in the injected `ProviderDescriptorRegistry`) `satisfies` the requirement. The registry-aware `RoutingRule.matches(context, registry)` overload is `suspend` (the registry is mutex-guarded) and defaults to the pure `matches`, so the five non-capability rules are unaffected.
- **Honour a seat's declared model** — tag the call with `routingContext.withSeat(seat)` (`roster/SeatRouting.kt:21`) and add `RoutingRule.ByTag(ExecutionTags.model("…"), configuration)` to the rule set, mapping the consumer's own model id onto the configuration that serves it. `ExecutionTags.effort` is the same for effort, which no provider parameter is derived from today: it is carried for a rule to match on.
- **Route by cost (cheapest-capable)** — when the first matching rule is a `ByCapability`, the relay does not stop at first-match: it ranks *all* capable `ByCapability` candidates with `CheapestCapableFirst` and resolves to the cheapest (`CognitiveRelayImpl.selectCheapestCapable`, `:189-215`). The order is `ModelDescriptor.routingCostPerWatt` ascending — 0 for a `CostPolicy.Free` model, otherwise its metered `costPerWatt` (`capability/ModelDescriptor.kt:73-74`) — with `ModelDescriptor.modelName` as the stable tie-break, not `providerId` (`capability/CheapestCapable.kt:9-10`). `CostPolicy` itself carries no rate: it is `Free` or `Metered` (`capability/CostPolicy.kt:14-21`), and the number lives on the descriptor. "Prefer on-device" is the limiting case — a local provider priced `CostPolicy.Free` (0W) always wins. The choice is observable via `RoutingEvent.RouteResolved` (chosen / runner-up / `savingsVsRunnerUp`), a sibling to `RouteFallback`. Single-candidate matches and all non-capability rules keep pure first-match. Rates are provider *data* in the registry; selection never hardcodes them. `RouteCostReporter` prints a deterministic dry-run of cheapest route + Watt cost per step across the launch Arcs.
- **Supply your own model catalog** — implement `ModelDescriptorSource` (a `fun interface`; `suspend fun load(): Result<List<ModelDescriptor>>`) and either build the registry from it up front with `InMemoryModelDescriptorRegistry.from(source)`, or pass it alongside a seed so routing works from the bundled catalog until the first load lands. Calling `refresh()` re-reads the source, so model→rung assignments change while the process runs — no relay reconstruction, no framework release.
- **Bind an on-device engine** — implement `LocalInferenceEngine` on the platform (on Apple, subclass `SwiftLocalInferenceEngine` in Swift and adapt it with `toLocalInferenceEngine()`), then build an `OnDeviceInferenceBinding` on it: that is a `DispatchingUpstreamLlmClient` sharing one `ModelDescriptorRegistry` with a `CognitiveRelayImpl`, plus the monitor. The binding attributes a capacity snapshot that names no provider to the on-device one, so the availability gate opens for an engine written against the text-only contract. `OnDeviceInferenceSession.create(engine, database)` does this for the single-prompt case; `ArcSession.create(arcConfig, projectDirPath, maxFlowTicks, database, engine, cloud)` does it for an Arc run, handing the binding's relay and client to `AmpereRuntime`. No Arc step is eligible for the device (AMPR-459), so there every call goes to `cloud` — a step with no floor on its configured model, a step floored at `ONE` cheapest-capable over the rated cloud models — and the engine is only probed. A null `cloud` leaves the runs nothing to run on: every step fails with `MissingUpstreamLlmClientException`, sending nothing. The client calls the engine with a `LocalGenerationRequest` (AMPR-462): the system message as `instructions` (null when there is none), the user message as `prompt`, the request's output cap as `maxOutputTokens` (`max_tokens`, which the service sets, or `max_completion_tokens`, the tighter when both are set), and its `temperature` only where it carried one. An engine implements `generate(prompt)` at the least; `generate(request)` defaults to handing it the request's `flattenedPrompt` — `System: …`, a blank line, `User: …`, byte for byte what the client sent before — so an engine written against the prompt form compiles unchanged and never sees the budget, and `SwiftLocalInferenceEngine` defaults the same way. `tokenCount(request)` defaults the same way too, to the engine's count of that string. Any other request — anything but a system message followed by a user message, or a user message alone — has no faithful split and reaches `generate(prompt)` flattened, as before. Apple's engine overrides the request form: `LanguageModelSession(instructions:)`, then `respond(to:options:)` with `GenerationOptions(temperature:maximumResponseTokens:)`, one session per call, the temperature clamped to Apple's documented 0–1 and the cap sent only when it is positive. A reply that reaches its cap is cut short by the framework without an error — asked to count from 1 to 100 under a 16-token cap, the model stopped at 6 — so a capped call answers. This is a contract fix and no quality claim: AMPR-372 measured the `instructions` form on its 15 hardest cases and 27 of 30 replies were still wrong. A JVM host cannot call FoundationModels at all, since it has no C or Objective-C headers, so `ampere-cli` reaches the model through a Swift helper process (AMPR-375): `HelperLocalInferenceEngine` speaks `ampere-helper`'s versioned stdio protocol to a child spawned through `ProcessGroups`, passes a request's parts and counts a request the way Apple's engine does, and reads a helper that is missing, too old or not answering as unavailable with `LocalUnavailableReason.HELPER_INCOMPATIBLE` or `HELPER_UNREACHABLE`, never as a failed call. `ampere-desktop` binds the same engine beside the CLI (AMPR-469): `OnDeviceHelperEngine.locate()` in `cli/ondevice/` is the one public way to it — the engine, or the locator's reason when the host has no helper — and the app renders `OnDeviceCognitionScreen` over `OnDeviceInferenceSession.create(engine, database)` with no cloud transport, its events in its own database. Its `prepareAppResources` copies the helper into the Compose resources directory on a Mac, where the locator looks through `compose.application.resources.dir`, so `run` and every packaged format carry it; the engine stays in `ampere-cli` until a host that does not depend on the CLI needs it.
- **Size a prompt for the device** — the on-device model's window is 4,096 tokens, measured against the live `SystemLanguageModel` on iOS 26.4.1, iOS 27.1 and macOS 27.0 (AMPR-373); the engine reads `contextSize` at every probe and the binding adopts whatever it reports. `OnDeviceInferenceSession` reserves 2,048 of those for output, so with `OnDeviceAssistantAgent`'s instructions about 7,900 characters of prompt fit and the relay refuses the rest as `PROMPT_TOO_LARGE` before the engine sees it; a prompt that reaches the model over its window is refused by the model itself ("exceeds the maximum allowed context size of 4096"). A short answer took under a second and a near-window prompt about three on an M-series Mac's simulator. Two overlapping `ask` calls each ran on their own `LanguageModelSession` and both answered, with the ledger showing two in flight. A refusal arrives in one of two forms the caller cannot choose between: the guardrail throws (`ON_DEVICE_GENERATION_FAILED`, in under a second) or the model answers with a one-line refusal in-band; both stay on the device. Since the engine passes the system message as instructions (AMPR-462), the recorded run's refusal has come in-band. `ampere-ios/iosAppTests/OnDeviceGenerationTests.swift` is the recorded run and skips where the model cannot generate — `availability` alone is not the test, because GitHub's hosted macOS runners report `.available` and then fail every generation with no model assets downloaded; `OnDeviceModelGate` generates one word first. The fit is sized by the engine's own count when the engine has one (AMPR-460), of the request the engine is handed (AMPR-462): `LocalInferenceEngine.tokenCount(request)` returns what a `LocalGenerationRequest` costs the model as input, or null; `DispatchingUpstreamLlmClient.countLocalTokens` exposes the bound engine's answer the way `probeLocalCapacity` exposes capacity; and both sizing sites — `OnDeviceInferenceSession.ask` and the service's fit — ask it for the request `LocalUpstreamLlmClient.generationRequestFor` says the call will hand the engine, and add the output budget. The default is the engine's `tokenCount(text)` of the request's `flattenedPrompt`, exactly what a prompt-only engine is handed, so an engine that counts only strings is sized as before. A string count misses what an engine wraps around a call: Apple's framework puts every call in a system turn of its own, about 50 tokens, which the model bills — by its own usage report a one-line question under `OnDeviceAssistantAgent`'s instructions costs 137 input tokens, where the flattened string counts 87. So Apple's engine counts the transcript a session for the request starts from — the instructions entry, empty when there are none, then the prompt entry — and that count matched the billed input exactly on every prompt measured, with instructions and without (137, 190 and 740 tokens; 64, 117 and 667 without). `ampere-ios/iosAppTests/OnDeviceGenerationTests.swift` checks the count against the bill on iOS 27, the first release that reports usage. Apple's engine answers with `SystemLanguageModel.tokenCount(for:)` from iOS 26.4 and nil before it. With no count — no engine, an engine that cannot count, or one whose counter throws — the fit falls back to `PromptTokenEstimator`'s chars/4, unchanged, and a counter that throws is never a failed call. The estimate undercounts digit-dense text: against the model's own tokenizer the median prompt ran 0.89–1.02× the estimate, but a log with timestamps was 298 real tokens against an estimate of 192 (1.55×) and a search listing 1.17× (AMPR-372), and a prompt admitted on an undercount is one the model refuses mid-call as `ON_DEVICE_GENERATION_FAILED`. The count only sizes; it never makes a call eligible, and the fit still widens an existing requirement and never creates one.
- **Make work eligible for the device** — only display text is (AMPR-372), and it already has its path: `OnDeviceInferenceSession.ask`, which runs under `OnDeviceAssistantAgent` (floor `ZERO`, a 2,048-token output cap and a requirement sized to the window). A host with words for a person to read hands them to the session and nothing else, as the CLI's TUI does for `:ask` (AMPR-375): it binds its helper engine to that session alone and leaves the agents' transports unbound, because no loop call can use the device and an engine there would only add a probe and a token count to each one; a host that already holds an `ArcSession` bound to the engine calls `ArcSession.ask(prompt, systemMessage)` instead of building a second session over the same engine — it runs under `OnDeviceAssistantAgent` through the Arc's binding, belongs to no Arc run (its own run id, its `ProviderCall*` pair persisted through the session's door), is null when no engine is bound, and its answer goes back to the caller and nowhere else; a summary a step consumes or a label a run records is not display text and goes through the loop at `ONE` or above. An agent that runs the PROPEL loop, and an Arc step (which is such an agent), cannot declare `ZERO` — it is refused at construction (AMPR-459): floors only raise, so the code agent's `THREE` rules the device out for every call it makes, and that is the intended shape. Do not size a loop call for the device to make it fit — a prompt that fits is not thereby eligible.
- **Show when the on-device model is being used** — collect `OnDeviceInferenceMonitor.state` (or `OnDeviceInferenceSession.state`, or `ArcSession.onDeviceState` for an Arc, which counts the runs' calls and every `ArcSession.ask` alike; Swift uses `ArcSession.observeOnDeviceState` and `refreshOnDeviceAvailability`, and calls `ask` as `async`). `isInUse` is true from a call's start event to its completion; `availability` says whether the device could serve and carries the engine's reason code when it cannot. Construct the monitor with the dispatching client as its classifier. `ui/inference/OnDeviceInferenceIndicator` renders it in Compose. A surface that marks single calls on a shared bus as on-device asks `OnDeviceInferenceSession.classifier`, the session's own dispatching client, so a marked call and the indicator cannot disagree; the CLI's TUI does this for its event-pane marker and renders the state in its status bar in `OnDeviceIndicatorModel`'s words (AMPR-375).
- **Say where one answer came from** — `AgentLLMService.callDetailed` returns the provider and model with the text; pass them to the classifier. Those are the *served* ids when the transport named them, so `InferenceLocalityClassifier.localityOf` is asked about what ran rather than what was picked. Do not read it back off the event stream, which is dispatched asynchronously.
- **Report what served a call** — override `UpstreamLlmClient.callDetailed` and return a `ServedBy`. Name only what the transport knows; leave the rest null. A proxy's own rule goes in `routingReason` in the proxy's vocabulary — it does not have to look like a relay reason, and it reaches the trace on `ProviderCallCompletedEvent.servedRoutingReason`.
- **Reach a model through a gateway, pinned to its maker** — resolve a configuration on `AIProvider_OpenRouter` and hand the call to `OpenRouterUpstreamLlmClient`. The default `OpenRouterRoutingPolicy` lets only the maker's own hosting serve it, forbids fallback to other hosts and excludes hosts that may store or train on the data; a response from any other host is an `UpstreamHostMismatchException`, not a completion. The class does not fall back by itself: to fall back to the maker's direct key, wrap it in your own `UpstreamLlmClient` that catches its failures (but not the mismatch, which was already served) and calls the direct transport — its KDoc shows one.
- **Inspect a routing decision in tests** — call `resolveWithMetadata` instead of `resolve`. The returned `RoutingResolution.reason` is a free-form tag describing which rule matched ("phase=PLAN" / "default fallback").
- **Trace which model handled a phase** — `ArcTraceProjection.project(runId)` returns `ModelInvocationTrace`s keyed by phase, naming the model that *served* each call, with `routingReason` from the transport's own reason when it reported one and the paired `ProviderCallStartedEvent`'s otherwise.

## Anti-patterns

- **A `ZERO` floor on an agent that runs the PROPEL loop.** It makes every phase of that agent eligible for the device, PLAN included: an Arc step floored at `ZERO` sent PERCEIVE and PLAN to the device, and the calls the device could not take (reasoning steps, whose 4,000-token default cap cannot fit) went cheapest-capable over the whole catalog to `gemini-2.5-flash`, not to the agent's configured model. A step with no floor would have used its configured model. Declaring a step eligible for the device also downgrades its cloud fallback. Measured on AMPR-372; the rule is `ONE` or above wherever the loop runs, and since AMPR-459 the Arc manifest types and `SparkBasedAgent` refuse anything lower at construction.
- **Defaulting an agent's floor to `ONE` to keep it off the device.** A missing floor already keeps it off: with no requirement no `ByCapability` rule matches, and the call uses the agent's configured model, which cannot be the on-device one. An explicit `ONE` switches that agent to cheapest-capable routing over the whole catalog, which changes which cloud model serves it — a routing change, not a safeguard.
- **Rating a model that executes on the device above `ZERO`.** "A floor of `ONE` keeps the device out" holds only while every local descriptor is at `ZERO`: re-rate the on-device model to `ONE` — in a source, a YAML override or `register` — and it clears every loop agent's floor and wins on price. The registry refuses the catalog (AMPR-459); leave a local model at `ZERO`, or unrated.
- **Marking a cloud model `CostPolicy.Free` to make it the cheapest.** `Free` is the device's cost policy, and `executesLocally` reads it: the dispatching client sends that model to the engine, and the registry refuses it above `ZERO`. A cheap cloud model is `Metered` with a low `costPerWatt`.
- **Reading `ZERO` as "the device".** A `ZERO` floor admits every rated model — every cloud descriptor with a rung satisfies it, and cheapest-capable only prefers the on-device one because it is priced `Free`. When the device is unavailable or the prompt will not fit, the same floor routes to the cheapest rated cloud model. The one thing `ZERO` excludes that no floor does not is an unrated model (`rung = null`). "Eligible for the device" is a property of the kind of call, not of the number.
- **Raising a call's output cap to make room for a model's thinking.** The cap is the call's budget for its answer, and a thinking model spends it on thought first; a larger cap pays for thinking a short structured answer does not need, on every model the call might route to. Lower the effort instead, which only reaches the models that take one (AMPR-488).
- **Sending `max_tokens` to OpenAI directly.** OpenAI's o-series and GPT-5 onward reject it with a 400 and want `max_completion_tokens`, so a request that carries the cap under the older name never reaches the model (AMPR-501). The swap is keyed on the route, not the model: OpenRouter and Google's compatible endpoint document `max_tokens`.
- **Constructing an `AIConfiguration` in domain code "just for this one call".** That call won't appear in the trace with any routing reason, and the next person who needs to change the model has to find every such call.
- **Resolving `ExecutionAssignment.model` to an `AIConfiguration` inside the framework.** The id is whatever the consumer wrote — an alias, a provider id, a model that is not in any catalogue. Guessing a provider for it would route a call to a model the consumer never authorised and label it with the seat's declaration. The tag is the handle; the mapping is the rule set's.
- **Encoding routing in `if/else` inside `AgentLLMService`.** The relay exists *because* this gets unmanageable. Predicates belong in `RoutingRule`s where they're inspectable, ordered, and observable.
- **Importing a provider SDK from cognition code.** Even "temporarily" or "for a quick test" — the import lingers, and now `agents/domain/...` is provider-coupled.
- **Treating `routingReason` as an internal detail.** It is read by the trace and displayed to humans debugging cognitive runs. A blank or unhelpful reason ("matched") is a regression in observability.
- **Mutating `RelayConfig` fields directly to "hot-update" rules.** The `updateConfig` path emits the changes; direct mutation is invisible to subscribers and to the trace.
- **Labelling a call on-device because the relay selected the on-device model.** Selection is a decision; execution is a fact. With no engine bound, the selected configuration cannot run at all. Ask the client that ran it.
- **Treating the bundled transport as the "else" branch for every configuration.** It is the else branch for *cloud* configurations. A local-designated one with nothing to run on is a refusal, not a fallback; routing it to `bundled` because an engine is missing is exactly the egress AMPR-371 closed, and the 401 that came back hid the fact that the prompt had already left.
- **Building a placeholder `OpenAI` client for a provider that never dials out.** `createClient` defaults a missing url to OpenAI's host, so the placeholder is a live endpoint with an empty token. A provider with no legitimate host should fail on `client` read, not point somewhere.
- **Falling back to the cloud after the device failed.** It turns a visible failure into an invisible egress. If a step should run in the cloud when the device cannot, that is the availability gate's job, and it happens before the prompt goes anywhere.
- **Holding one `LanguageModelSession` for the engine's lifetime.** The contract is stateless; a session is not. A shared session accumulates transcript against the context window the prompt was measured for, leaks one call's content into the next, and traps when two calls overlap. One session per call. Counting tokens is stateless too: it is asked of the model, never of a session kept to count on (AMPR-460).
- **Sizing a call with a count of anything but the request the engine is handed.** The relay's fit is only as good as what it counted. The user turn alone drops the instructions, and a string count of even the whole flattened prompt drops the turns an engine wraps around the call — 50 tokens of Apple's 4,096-token window, billed on every call. Ask `countLocalTokens` for the `LocalGenerationRequest` from `LocalUpstreamLlmClient.generationRequestFor`, the split the client itself makes, and let the engine count what it sends; an engine that counts only strings is then asked for the flattened prompt it is handed (AMPR-462).
- **Wrapping an engine without forwarding `generate(request)`.** The interface's default flattens a request into `generate(prompt)`, so a decorator that overrides only the prompt form hands every call to the engine inside it flattened, and the instructions, the output budget and the temperature never arrive — silently, because the prompt still answers. `OnDeviceInferenceBinding`'s observed engine and `toLocalInferenceEngine()` forward both forms, and both forms of `tokenCount` for the same reason: a wrapper that counts only strings sizes every call by the flattened prompt, whatever its engine would have said.
- **Inventing an event to drive the indicator.** Everything the on-device read model needs is already emitted by the relay and `AgentLLMService`. A second signal for the same fact is a second thing to keep truthful.
- **Giving the relay and the client different registries.** The relay selects by a descriptor and the client dispatches by one; two catalogs let them disagree about whether a model is local, and a call the relay priced at 0W goes out on the cloud transport. `OnDeviceInferenceBinding` exists so there is one instance to share.
- **A second binding, or a second subscription, over one engine.** A host that builds its own `OnDeviceInferenceSession` beside an `ArcSession` bound to the same engine gets a second binding, ledger and indicator for one device; use `ArcSession.ask`. And a session built over a binding someone else holds must not follow the bus into it again: the binding's monitor counts what it is fed, so a second subscription folds every call twice. `OnDeviceInferenceSession.over` follows nothing for that reason (AMPR-461).
- **Building an engine-bound `AmpereRuntime` with no `eventApiFactory`.** The relay and the client then route and run on the device, and nothing persists the `ProviderCall*` pair under the run id — the trace shows no model calls and the on-device state never leaves `Unknown`. `ArcSession.create` supplies the factory whenever it has a database.
- **Reaching a decision model through `UpstreamLlmClient`.** A decision request has no messages and returns no text; squeezing it into a chat completion keeps one seam and drops the distribution, which is what the call exists to return. The Decide seam is `UpstreamDecisionClient`.
- **Reading a completed call's provider and model as the relay's decision.** Since AMPR-391 they are what *answered*. The relay's decision is on the start row, beside the `routingReason` that explains it. A consumer whose proxy routes server-side makes the two genuinely different, and a reader that treats them as interchangeable will attribute a cost to a model that was never called.
- **Publishing a second `ProviderCall*` pair from a consumer's own response.** That is the duplication the served seam removes: two pairs for one call, one of them naming a model that did not answer, and no way for a reader to tell which is which. Report a `ServedBy` and there is one pair, correct.
- **Substituting an engine-private model identity for the catalog's on the local path.** `LocalUpstreamLlmClient` reports the on-device provider and model the dispatch keyed on, deliberately. Two readers key on that pair: the on-device ledger balances a start against a completion on `(workflowId, agentId, providerId, modelId, cognitivePhase)`, and `DispatchingUpstreamLlmClient.localityOf` resolves a descriptor by model id. A name the catalog does not hold leaves the "generating now" indicator stuck on and labels a call that never left the device `CLOUD`. The engine's own reported model already reaches a surface through `LocalCapacity.modelId`.
- **Recording or pricing a routed call under the gateway's id.** `openrouter` in `providerId` matches no catalog row, so the call books no cost, and a reader grouping spend by maker sees a provider that makes nothing. The gateway goes in `via`; adding gateway rows to the pricing JSON to make the lookup hit would give one model two prices.
- **Reading a configuration's model before its provider.** `AIConfiguration_WithBackups` decides which of its configurations answers when its `provider` is read, and `model` and `wireModelId` follow that decision. Read the model first and the record can pair one configuration's model with another's route. `AgentLLMService` reads the route first for this reason.
- **Registering a routed model as a second catalogue row.** A model reached through OpenRouter is the model its maker serves, so it already has a `ModelDescriptor` under its maker's id. A second row keyed on the route would duplicate a `modelName` the registry rejects, or — under another name — give one model two rungs and two prices, and let cheapest-capable pick a route as if it were a different model. A route changes how a chosen model is reached, never which model is chosen.
- **Rebuilding the relay to change a model's rung.** The registry is the mutable surface — `refresh()` (whole catalog) or `register()` (one descriptor). Tearing down a live relay drops the rule set and every in-flight reasoning session along with it.
- **Relying on a gateway's default host choice when a consumer has promised who receives a prompt.** OpenRouter load-balances a model across hosting companies by price unless told otherwise, so the company that receives the prompt is the gateway's pick, not the consumer's. Pin it per request with `OpenRouterRoutingPolicy`, and believe the response's named host rather than the request's preference — `OpenRouterUpstreamLlmClient` checks it and fails closed.
